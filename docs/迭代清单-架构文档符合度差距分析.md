## 迭代 0：安全专项 —— 真沙箱替换 `new Function`（P0）

**现状**：事件脚本、数据转换脚本、自定义组件源码均以 `new Function` 在页面主环境执行，
注释与文档均称"沙箱"，但脚本可 freely 访问 `window / document / localStorage / cookie`，
任一租户发布的脚本即可对其他观看者发起 XSS / 凭证窃取，属高危安全缺陷。

**涉及文件**：

- `apps/frontend/builder-server/src/views/preview/runtime/event-runtime.ts`（L103、L240）
- `apps/frontend/builder-server/src/views/preview/runtime/data-runtime.ts`（L236）
- `apps/frontend/builder-server/src/views/editor/components/DataBindingPanel.vue`（L91）
- `packages/shared-types/src/dto/component.ts`（"沙箱运行"字段注释）

**改造方案**：

1. 抽象 `ScriptSandbox` 接口（execute/terminate/超时），实现基于 **Web Worker + iframe sandbox** 的执行层，脚本与宿主完全隔离，仅通过 `postMessage` 传递结构化数据（data/ctx 序列化注入）；
2. Worker 内以 `new Function` 执行 + 严格 CSP（`worker-src blob:`），配合执行超时中断（如 100ms 转换 / 1s 事件）；
3. 编辑器预览面板与运行时共用同一沙箱实现，消除 DataBindingPanel 与 event-runtime 的双标。

**验收标准**：脚本中访问 `window` 抛 ReferenceError；恶意死循环脚本被超时终止且不影响页面渲染；现有场景/组件脚本回归通过。

**方案（建议改代码而非改文档，"server" 后缀只留给后端服务）**：

## 迭代 2：文档明确要求但未实现的功能（P1）

### 2.1 多人实时协同编辑（Yjs + WebSocket）

**现状**：nginx `/ws` 注释宣称 Yjs 协同，实际无 `yjs` 依赖；`RealtimeGateway` 仅做 IoT/场景推送。
**方案**：

- 后端新增 `collab` 模块（或独立 `y-websocket-server`），基于 `y-websocket` 协议 + `hocuspocus/server`，以场景 DSL（`scene.content`）为 Y.Doc，JWT 鉴权复用 RealtimeGateway 模式；

- 提供在线用户/光标presence。
  **裁剪选项**：若本期不做，必须同步删除 nginx 注释、README、文档 3.3/7.3.6 中的 Yjs 表述，避免虚标。

### 2.2 Cesium Ion 集成 + 代理服务（TR002）

**现状**：仅 `env.d.ts` 一个 token 类型声明，无 Ion 资源加载、无代理。
**方案**：

- 前端 `imagery.ts` 支持 `IonResource.fromAssetId`（地形/影像/3D Tiles），token 走 `.env`；
- 后端 `widget-server` 新增 `cesium-ion` 子模块：token 服务端保管 + URL 短链签名代理（避免 token 泄漏到浏览器），对应文档 `cesium-ion-server` 职责。

### 2.3 OpenLayers 二维地图（BR002）—— 决策项

**现状**：完全缺失，二三维联动只有 Cesium↔Three 相机同步。
**方案 A（补齐）**：`rendering-engine` 新增 `ol/` 引擎适配层 + 2D 地图组件（复用 POI 体系），接入 camera-sync 做二三维联动。
**方案 B（裁剪）**：产品定位不含 2D 大屏地图，则修订文档 BR002/技术选型，删除 OpenLayers 表述。

## 迭代 4：部署与 CI/CD（P1）

### 4.1 部署栈决策：Nginx vs 文档 Caddy + PM2

**现状**：生产镜像链用 Nginx（HTTP/2、限流、强缓存、SPA、WebSocket 齐备，质量优于 Caddy 简单配置），但无 PM2、无 `ecosystem.config.js`，nginx `widget-server-1/2` 双实例无编排支撑。
**方案**：

- 决策保留 Nginx，**修订文档**（3.3/5/7.3.5 的 Caddy→Nginx），并把 PM2 定位为"裸机部署可选路径"；
- 补 `docker-compose.prod.yml`：widget-server × 2 实例 + nginx + postgres/redis/minio，与 upstream 名称对齐，验证滚动重启；
- 或补 `ecosystem.config.js`（cluster、max_memory_restart、env 分段）支持无 Docker 场景，二者至少落其一。

### 4.2 CI/CD（TR003）

**现状**：零流水线。
**方案**：GitHub Actions（或 Gitee Go）三条流水线：

1. PR：`pnpm typecheck` + `lint` + `test`（增量）+ 前端构建产物体积报告；
2. main 合并：双 Dockerfile 构建推 registry；
3. tag：生产 compose 部署（可选环境门禁）。

### 4.3 工程化规范补全（文档 6.3）

- Stylelint（`*.vue <style>` + css，配 `postcss-html`）；
- cspell（仓库含大量 draco/basis/glb 等专有名词，需定制词典）；

## 迭代 8：环境可靠性与数据演进（初始化实测发现，P0/P1 混合）

> 本项全部来自 2026-09-18 实际执行 `infra:up → build:pkg → schema:init → typecheck → 服务冒烟` 的一手结果，非推测性风险。

### 8.1 基础设施镜像源失效（✅ 已止血，⏳ 需防回归）

**现象**：`pnpm infra:up` 直接失败：`pull access denied for minio/minio, repository does not exist or may require 'docker login'`。
**根因**：MinIO 已将镜像从 Docker Hub 撤下，compose 中 `minio/minio:RELEASE.2024-08-17T01-24-54Z` 是死引用（与本网络无关，任何新克隆都会卡在此处）。
**已改**：`docker/docker-compose.dev.yml` 的 minio 镜像改为 `quay.io/minio/minio:RELEASE.2024-08-17T01-24-54Z`，实测 dt-postgres/dt-redis/dt-minio/dt-mosquitto 四容器全部 healthy。
**待办**：

1. 迭代 4.1 落地 `docker-compose.prod.yml` 时同步使用 quay.io 源，避免复制旧写法；
2. CI 增加镜像可拉取性冒烟（`docker compose config --quiet` 校验 + 基础镜像 pull 检查），防同类回退。

### 8.2 Schema 无版本化迁移能力（✅ 已止血，⏳ 本项为根治重点）

**现象**：`docker/data/postgres` 持久卷由旧版 schema 初始化，重放 `01_schema.sql` 时 `CREATE TABLE IF NOT EXISTS` 不给已存在的表补列，导致 `CREATE UNIQUE INDEX ... ON biz_scene (publish_token)` **报列不存在直接失败**；同时 `biz_file.md5` 仍是 `VARCHAR(32)`，写入 64 位 sha256 指纹会溢出报错。
**已改（止血）**：`01_schema.sql` 补两段幂等升级 DDL（`ALTER TABLE biz_scene ADD COLUMN IF NOT EXISTS publish_token`、`ALTER TABLE biz_file ALTER COLUMN md5 TYPE VARCHAR(64)`），实测 `pnpm schema:init` 在陈旧卷上可完整重放，两列已校验为 `character varying(64)`，且不影响全新库首次初始化。
**根因（未根治）**：`src/database/data-source.ts` 已声明 `migrations: ['src/database/migrations/*']` 与 `migrationsTableName: 'sys_migrations'`，但 `src/database/migrations/` **目录不存在**、库中 **无 `sys_migrations` 表** —— 根 `package.json` 的 `pnpm db:migrate` 是条死路。schema 演进完全依赖"全量 SQL 重放 + IF NOT EXISTS"，8.2 这类陈旧卷缺陷必然复发。
**方案**：

1. 建 `src/database/migrations/`，用一个 `InitSchema` 基线迁移收编现有 `01_schema.sql`，此后所有 DDL 变更一律走 `migration:generate`；
2. `01_schema.sql` 降级为"全新库一次性基线"，文件头注明"结构变更禁止直接改本文件"；
3. 移除本次临时加入的两段 `ALTER`（由对应 migration 取代，避免双份真相）；
4. CI 增加门禁：实体有 diff 但无新增 migration 文件 → 失败。
   **验收标准**：`pnpm db:migrate` 在"全新库"与"陈旧卷库"两种起点上均执行成功，`sys_migrations` 有版本记录，`migration:revert` 可回滚上一版。

### 8.3 环境变量入库策略（✅ 已修，⏳ 三项收尾）

**现象**：`.env.dev` 被 git 跟踪，工作区版本含真实第三方密钥（Tripo3D `tsk_...`、DeepSeek `sk-...`），一旦 push 即泄漏到 `origin`（github.com/LK-Improving/ai-twin-vision）。
**已改**：`.gitignore` 纳入 `.env.dev/.env.test/.env.prod` 并保留 `!.env.example`；`git rm --cached .env.dev`（本地文件保留）；`.env.example` 补齐 L3 AI 生成段空占位符，成为唯一入库模板。已核对 `HEAD:.env.dev` 不含这些密钥 → **未进 Git 历史，无需重写历史**。
**待办**：

1. 提交当前暂存的删除与 `.gitignore` 变更，否则策略未真正生效；
2. 若这两个 Key 曾被截图/传阅，在 Tripo3D、DeepSeek 控制台轮换；
3. 迭代 4.2 的 CI 接入 secret 扫描（gitleaks / trufflehog）作为 PR 门禁。

### 8.4 本机端口冲突（✅ 已修，需文档化）

**现象**：本机 5432 被原生 `postgresql-x64-18` 系统服务占用、6379 被既有 `local-redis` 容器占用，标准端口的 compose 无法启动。
**已改**：`.env.dev` 采用 5433/6380；因 compose 宿主端口映射读同一份 env（`--env-file .env.dev`），后端连接配置自动同步错位，未停止本机任何既有服务；`.env.example` 已加注释说明该约定。
**待办**："端口被占即改 env、不改 compose"写入 README 启动章节（归入迭代 6 第 5 条）。

### 8.5 外部服务配置笔误（✅ 已修，⏳ 需加校验）

**现象**：`.env.dev` 中 `TEXT3D_API_URL=hhttps://openapi.tripo3d.com/v3` 多一个 `h`。该段设计为"URL 与 Key 同时非空才启用，否则自动降级为程序化生成（不报错）"，笔误使 L3 文本生成 3D **静默失效**，表现为"功能像没生效"但无任何日志线索。
**已改**：修正为 `https://`。
**待办**：`configuration.ts` 对所有外部服务地址增加启动期校验——值非空但 URL 非法（协议段异常、不可解析）时打 WARN 日志并标注"已降级"，消除这类静默失效。
