## 迭代 0：安全专项 —— 真沙箱替换 `new Function`（P0，✅ 已实施 2026-09-18）

**现状**：事件脚本、数据转换脚本、自定义组件源码均以 `new Function` 在页面主环境执行，
注释与文档均称"沙箱"，但脚本可 freely 访问 `window / document / localStorage / cookie`，
任一租户发布的脚本即可对其他观看者发起 XSS / 凭证窃取，属高危安全缺陷。

**涉及文件**：

- `apps/frontend/builder/src/views/preview/runtime/event-runtime.ts`（原 L103、L240）
- `apps/frontend/builder/src/views/preview/runtime/data-runtime.ts`（原 L236）
- `apps/frontend/builder/src/views/editor/components/DataBindingPanel.vue`（原 L91）
- `packages/shared-types/src/dto/component.ts`（"沙箱运行"字段注释）

**改造方案**：

1. 抽象 `ScriptSandbox` 接口（execute/terminate/超时），实现基于 **Web Worker + iframe sandbox** 的执行层，脚本与宿主完全隔离，仅通过 `postMessage` 传递结构化数据（data/ctx 序列化注入）；
2. Worker 内以 `new Function` 执行 + 严格 CSP（`worker-src blob:`），配合执行超时中断（如 100ms 转换 / 1s 事件）；

## 迭代 0 实施记录（2026-09-18）

**新增沙箱层** `apps/frontend/builder/src/sandbox/`（路径已随迭代 1.1 改名）：

| 文件                | 职责                                                               |
| ------------------- | ------------------------------------------------------------------ |
| `protocol.ts`       | 宿主↔Worker 报文协议、超时配额、能力白名单（双处登记的单一真相源） |
| `guard.ts`          | 静态守卫：先抹除注释与字符串再扫危险标识符，避开误报               |
| `sandbox.worker.ts` | 唯一执行环境：Worker realm + `with(proxy)` 全局遮蔽 + 能力代理     |
| `capabilities.ts`   | 宿主侧能力分发器：白名单、同源校验、返回值 JSON 化                 |
| `script-sandbox.ts` | 门面：共享线程（转换/表达式）+ 独占线程（事件脚本）+ 超时硬中断    |

**实际选型差异**：原计划中的 iframe sandbox 被取消。iframe 方案必须把宿主函数注进子文档，
任何返回的宿主对象都能顺着 `constructor` 链摸回主 realm；改为 Worker + 能力代理后，
跨边界值全部被强制 JSON 化，从机制上消除该逃逸面，代价是能力调用变为异步。

**验收证据**：

- 19 个 vitest 用例全绿（守卫命中与误报边界、白名单每项都有实现、同源校验、节点视图不泄露 props）；
- 浏览器端到端（真实 Worker）：`typeof structuredClone` 页内为 function、沙箱内为 undefined；
  顶层 `this` 不再是全局对象；死循环脚本在 3000ms 被终止且不影响同期其他脚本；
  超时后线程自动重建；`ctx.viewer.destroy()` 被拒（未授权）；外部域 `ctx.request` 被拒；
- 真实链路回测：`DataRuntime` 静态数据→转换→`__data` 注入生效；坏脚本回退原数据并经 onError 上报；
  `EventRuntime` 条件放行、能力回写变量、切换节点可见性均生效；
- 主线程 `new Function` 已归零（仅 Worker 内部保留一处，为执行用户脚本的设计必需）；
- `pnpm typecheck`、`eslint`、`pnpm build` 全部通过，Worker 正常产出独立 chunk；测试环境新增
  `vitest.config.ts`（不复用 vite.config，避开 cesium 插件参与单测转换）。

**行为变更（需告知脚本作者，已写进 `SCRIPT_ENV_NOTES` 并在脚本编辑器内展示）**：

1. 取值类能力为异步，必须 `await`（旧脚本的同步 `ctx.viewer.xxx` 仍能触发副作用，只是拿不到返回值）；
2. 变量读写改用 `ctx.getVar/setVar` 或 `ctx.variables` 快照，不再持有 viewer/node 实例引用；
3. 沙箱内无 `setTimeout/setInterval`，延时请用动作自带的 `delay`；
4. 静态数据绑定现在也会执行 `fieldMap` 与转换脚本（与编辑器预览一致，修掉了运行时/预览双标）。

**残余风险与后续项**：

- 守卫为正则级，字符串拼接可绕过并摸到 Worker 自身的 `fetch`（无 DOM、无主线程 JWT，但存在数据外发面）；
  收口需要 CSP `connect-src` 或 SES `lockdown()`，归入迭代 4.2 后的安全加固项；
- 自定义组件 `sourceCode` 字段实际无执行入口（WidgetRenderer 只走内置注册表），本次未虚假声称已沙箱化，
  已在类型注释中明写；将来开放时直接复用本沙箱；
- 沙箱实现应在迭代 1.2 上提为 `packages/data-processor` 以供其他包复用，本迭代先落在 app 内。

**复盘更正（2026-09-20）**：上面那句“推送到 GitHub 后首次才会跑绿”其实把结论说错了 ——

**流程教训**：本地把每条 step 的等价命令跑通 ≠ CI 已生效。“等价命令验证”只能证明
作业内容是对的，证明不了作业能被调度。接入流水线后必须做两件事之一：
用 `actionlint` 类工具校验 Actions schema（不是普通 YAML 解析！js-yaml 能过而 GitHub 拒收），

普通 YAML 解析通过完全不等于 workflow 合法 —— 本次就是这么误判的。

**立项时现状**：零流水线。

1. PR：`pnpm typecheck` + `lint` + `test`（增量）+ 前端构建产物体积报告；

  - run 35602382826：`[diag]` 显示 `节点 DOM 数量 = 1`，直接指出事件绑定用例隐含假设
    「被选中的场景至少渲染出 2 个节点」—— 本地节点多所以一直绿，CI 上挑到的场景只有 1 个。
  - run 35623879076：修完上一问题后反而弄红了 publish / sandbox 用例，`[diag]` 显示
    `lib-item 数量 = 0` 而 `tree-row 数量 = 3`。根因是**测试隔离被我破坏**：事件绑定用例
    去 PATCH 了「列表第一个有节点的场景」，PATCH 把该场景 `updated_at` 顶到最新 →
    场景列表顺序变了 → 后续用例打开的是另一个场景（其组件库按场景类型过滤后 `.lib-item` 为 0）。

  应该由用例自己创造数据，而不是去现有数据里碰运气。

### 8.2 Schema 无版本化迁移能力（✅ 已根治 2026-09-19）

**现象**：`docker/data/postgres` 持久卷由旧版 schema 初始化，重放 `01_schema.sql` 时 `CREATE TABLE IF NOT EXISTS` 不给已存在的表补列，导致 `CREATE UNIQUE INDEX ... ON biz_scene (publish_token)` **报列不存在直接失败**；同时 `biz_file.md5` 仍是 `VARCHAR(32)`，写入 64 位 sha256 指纹会溢出报错。
**已改（止血）**：`01_schema.sql` 补两段幂等升级 DDL（`ALTER TABLE biz_scene ADD COLUMN IF NOT EXISTS publish_token`、`ALTER TABLE biz_file ALTER COLUMN md5 TYPE VARCHAR(64)`），实测 `pnpm schema:init` 在陈旧卷上可完整重放，两列已校验为 `character varying(64)`，且不影响全新库首次初始化。
**根因（未根治）**：`src/database/data-source.ts` 已声明 `migrations: ['src/database/migrations/*']` 与 `migrationsTableName: 'sys_migrations'`，但 `src/database/migrations/` **目录不存在**、库中 **无 `sys_migrations` 表** —— 根 `package.json` 的 `pnpm db:migrate` 是条死路。schema 演进完全依赖"全量 SQL 重放 + IF NOT EXISTS"，8.2 这类陈旧卷缺陷必然复发。
**方案**：

1. 建 `src/database/migrations/`，用一个 `InitSchema` 基线迁移收编现有 `01_schema.sql`，此后所有 DDL 变更一律走 `migration:generate`；
2. `01_schema.sql` 降级为"全新库一次性基线"，文件头注明"结构变更禁止直接改本文件"；
3. 移除本次临时加入的两段 `ALTER`（由对应 migration 取代，避免双份真相）；
4. CI 增加门禁：实体有 diff 但无新增 migration 文件 → 失败。
   **验收标准**：`pnpm db:migrate` 在"全新库"与"陈旧卷库"两种起点上均执行成功，`sys_migrations` 有版本记录，`migration:revert` 可回滚上一版。

### 8.2 实施记录（2026-09-19）

**结构**：新增 `src/database/migrations/`，两个迁移：

**两种起点均实测（验收标准逐条对账）**：

- 陈旧库（已被旧流程建好）：`pnpm db:migrate` 成功；跑前跑后对比
  `publish_token=1 / md5=64 / hypertable=1 / biz_scene=2 / sys_user=4` **完全一致**（表数 +1 仅为新增的 `sys_migrations` 记账表），
  证明幂等且不覆盖数据；`sys_migrations` 写入两条版本记录。
- 全新空库（临时 `digital_twin_fresh`）：基线建出 24 表、`publish_token` 存在、md5=64、**hypertable 成功建立**、
  `sys_user=0`（证明结构与种子已正确分离）；`db:seed` 后 `sys_user=4`。
- **回滚可用**：`migration:revert` 后 `publish_token=0 / md5=32`；再次 `db:migrate` 恢复 `1 / 64`，版本记录回到 2 条。验证后临时库已删除。

**两个实测才发现的坑（值得记住）**：

1. 迁移文件用 14 位日期名（`20260919120000-…`）时，`sys_migrations.timestamp` 被削成 `260919120000`；
   改用 TypeORM 惯用的 13 位毫秒时戳（`1789000000000-…`）后记录完整。**命名必须跟着工具约定走。**
2. 漂移检查首次跑出 258 行“伪漂移”：`01_schema.sql` 用内联 `REFERENCES` 未写 `ON DELETE`，且带

   处理方式不是关掉检查，而是**分类计数**：实测 123 条差异中外键 34+34、索引 32+32、注释 42、默认值 15，

   据此 `--strict` 本地 exit 0，才能放进 CI 当硬门禁。

**CI**：新增 `migration` 作业（PR 有生效）：空库 `db:migrate` → 断言版本记录/表数/`publish_token` → `db:seed` 跑两遍验证幂等 → `db:check-drift`。

**已知局限**：SQL 基线声明的外键集合与 entity 建模的关系不等价（只是被分类排除；具体成因见 8.6，
那里也记录了我先后两个错判），且 `01_schema.sql` 与迁移共用带来
“docker initdb 路径不写版本号”的遗留（需 `db:migrate` 补登一次，已在 README 说明）。彻底解法见下方 8.6。

### 8.6 SQL 基线外键与 entity 关系集不一致（P2，诊断已修正 2026-09-19）

**两次错误假设均被实测否掉**（保留在此以免后人重复踩坑）：

- 假设 A“SQL 缺 `ON DELETE`”：错。库里 `biz_component_creator_id_fkey` 的 `confdeltype='a'`（NO ACTION），
  与 TypeORM 期望的 `ON DELETE NO ACTION` 完全一致，却仍被判定需重建。
- 假设 B“外键命名不一致（Postgres 自动名 vs `FK_<sha1>`）”：几乎无效果。实验过自定义
  `namingStrategy.foreignKeyName` 输出 `<表>_<列>_fkey`，漂移探针中外键重建仅从 34 降到 32，
  因此该实验已**完全回退**，不留未验证的机制。

**实际根因（已验证）**：`01_schema.sql` 给几乎所有表都加了内联 `REFERENCES` 外键（共 34 个），
但很多 entity（如 `ComponentEntity`）**只有 `tenantId` / `creatorId` 普通列，没有 `@ManyToOne` 关系**。
TypeORM 的差异比对以 entity 元数据为准，因此它永远会试图删掉这些“自己不认识”的外键，
并为自己声明的关系重建另一套约束 —— 这 60+ 条噪声是**建模层面不一致**，不是配置能抹平的。

**可选方案（需产品/架构先定方向，不是小改）**：

1. 给需要的 entity 补齐 `@ManyToOne + @JoinColumn` 关系声明（约 34 处），让元数据追平基线；
   代价：关系加载可能改变查询行为与序列化输出，需配合接口回归；
2. 或者承认“外键由 SQL/DBA 拥有，不由 TypeORM 管理”，在文档与脚本里明写这一约定为长期状态；
3. 废弃 `01_schema.sql`、改由 `migration:generate` 从 entity 生成全量基线（彻底单一真相，
   代价是失去手写表注释与部分索引调优）。

**当前状态**：`check-migration-drift.mjs` 的分类排除已验证有效（列/表/类型级净变更为 0 才能过 strict），
CI 已按此接入；上述方案 1/3 属于结构重构，不在本迭代范围。
